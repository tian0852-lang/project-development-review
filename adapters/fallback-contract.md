# Minimal fallback — project-development-review 2.2.0

<!-- fallback-version:2.2.0 -->
<!-- fallback:start -->
If the full package or a mandatory reference is unavailable, state the missing paths and available capabilities. This is a minimal safety fallback, not a claim of full Skill execution.

1. Collect goal, users, core task, included/excluded scope, target platforms, new/change/mixed work units, real project_root (or null), separate review_root, README location and first requirement language. Ask up to three questions at a time.
2. Select exactly one Figma or MasterGo source with link, exact nodes and current screenshots. Do not invent unreadable prototype behavior or count pages from a parent screenshot. Produce and render a PAGE & RESOURCE CHECKPOINT with candidate page count, every page row, every icon/image resource, source IDs, original/design/export/runtime dimensions, scale, save root and evidence limits. Wait for explicit approval or correction of that displayed version.
3. Keep an evidence table (ID, type, source/location, readable scope, limitations) separate from item approval (Draft, Pending confirmation, Approved, Out of scope, Invalidated). Keep a decision table (ID, facts, options, suggestion/rationale, affected IDs, blocking level, user decision/event). Render an OPEN QUESTIONS PANEL containing every unresolved decision in the conversation; ask at most three questions this turn without hiding the rest. Never treat a suggested default as approved.
4. Request the mandatory core references and templates listed above before their stages. Without them continue intake/page drafts only; do not fabricate a complete v2 package or final handoff. After receiving them, produce seven specs, then obtain genuine specification approval, then a read-only assessment card and proposed plan, then genuine plan approval, then the implementation handoff. Reuse the approved version; do not demand another identical plan.
5. Maintain review-manifest.json as the state index: schema_version, project/review IDs, mode, roots, source, stage, versions (including resources), artifact IDs/paths/versions/completion, evidence, resources, resource save records, items, decisions, acceptance, confirmation_events, invalidations, preconditions, external_dependencies, changes, active_cards, validation. Use the actual schema/template once attached, not invented field shapes. Implementation pointer stays null before plan approval.
6. Record confirmation from the real current user and displayed version, never quoted/negated/example text. Keep visible wording/reference, scope/exclusions/conditions and source limitations; leave unavailable time/message ID null. Historical summaries remain Recorded but unverified. Files use real SHA-256; text uses locatable frozen versions without invented hashes.
7. With no file capability output complete readable Markdown and manifest drafts in the conversation, labelled "Text-only delivery / not filesystem-validated". Do not claim files were saved, links checked, hashes computed or validation executed. Draft serialization awaits filesystem validation and provenance review before Ready.
8. Never implement code or perform dependency/native/Git writes. For change/mixed mode compare the historical and current resource inventories and classify deltas; unknown impacts remain unresolved. Save only confirmed resources under review_root/assets when the capability is actually available, record conflicts and never overwrite silently. Stop at the earliest stage missing required evidence/rules.
