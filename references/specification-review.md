# Specification review

At every specification turn render the OPEN QUESTIONS PANEL. Before specification confirmation also render the SPECIFICATION SCOPE CHECKPOINT from conversation-output-contract.md; do not rely on a document-only link.

After valid page/resource approval, draft seven specs using the required templates and common review-meta contract. Cover:
00 users, context, goals and success; 01 current scope/exclusions/priorities; 02 state, navigation, parameters, return retention, dialogs and recovery; 03 visual components/tokens/copy and references to the approved page resource inventory; 04 real/mock data/privacy/submission constraints; 05 platform-specific acceptance and evidence; 06 differences, decisions and known owners.

Separate future full product ambition from this round's UI-only delivery. Product target platforms must be set before specification approval; SDK versions may be proposed in the plan. Do not force a nontechnical user to preselect every engineering detail.

Every implementable requirement gets a stable item ID linked to evidence, decisions and acceptance. Resource IDs used by implementable requirements must resolve in the approved resource inventory and must preserve original/design/export/runtime dimensions. Use decision-policy.md for unresolved matters. Mark nonapplicable content with a reason, not empty cells or unresolved placeholders. Source observations are not whole-spec approval.

Before specification confirmation, present version, included item IDs/platforms, exclusions, limits and open-decision impact. Run specification_preflight checks; do not create the assessment card until the actual specification event is valid.

For explicitly requested beginner practice, suggest 2–3 pages, one main navigation flow and 1–2 simple confirmation/information dialogs, excluding login, network calls, complex animation, permissions and deep navigation. This is a suggested exercise boundary, not an automatically approved product rule.
