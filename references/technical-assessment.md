# Technical assessment

After approved specifications and resource references, issue exactly one active technical-assessment-task-card. It authorizes read-only analysis and plan output, not implementation. Read confirmed specs, README, resource inventory and baseline before necessary source inspection.

Draft plan proposals may be new. Include actual or proposed file paths, create/modify/reuse/replace actions, component responsibilities, state/data flow, navigation parameters/return retention, dialog behavior, resource paths/scales/dimensions and save preconditions, dependency/resource/config impacts, compatibility/regression risks, acceptance coverage, initialization for new projects and implementation preconditions. Local calculation proposals must not use eval().

Before plan approval resolve scoped business conflicts, mutually exclusive options and undecided platform baseline choices. Proposed SDK choices can be approved with the plan. Record exact spec/baseline dependencies.

After valid plan approval, generate the implementation-task-card, approval record and developer-handoff pointing to that plan event/version. Downstream tools verify baseline/conditions and execute only the approved scope after separate development authorization; they do not regenerate or reapprove the same unchanged plan. Stop affected work if baseline changes or deviation is needed. The review Skill never implements.
